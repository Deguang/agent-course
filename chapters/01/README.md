# Chapter 01 · agent 的心脏:一个 loop

## 这一章要建立的一个念头

先别管代码。想象你雇了一个**很聪明、但被关在小黑屋里的助理**:

- 他脑子很好,能读你给的对话、能想、能决定下一步该干嘛。
- 但他**手脚被绑住**——读不了你电脑上的文件、跑不了任何命令、上不了网。

这就是"模型"(model)。它只能**想和说**,不能**做**。

那它怎么帮你"读 README 并概括"?它自己做不到——所以屋外得有个**跑腿的**,听助理指挥去真正干活。
一共三个角色,别搞混:

> **你(用户)**:"读一下 README,然后概括这个项目。"(发出请求)
> **助理(模型)**:"我读不了文件,请跑腿的去执行 `read`。"(他只能**提议**,不能自己读)
> **跑腿的(loop)**:(真的去读了文件)"这是 read 的结果,内容是……"(它**执行**,并把结果递回给助理)
> **助理(模型)**:(看到内容)"好,这是一门 agent 课程。"(**收尾**,答复你)

注意:执行 `read` 的是**跑腿的(loop)**,不是助理、也不是你。你只负责"提出请求"和"拿到最终答复";
中间那些脏活——真去调工具、把结果喂回给模型——是跑腿的干的。

**这个"跑腿的",就是 agent loop。这一章你要写的,就是它。**
它是所有 agent 的心脏——ChatGPT 插件、Claude Code、Cursor,内核都是这个来回。

## 一句要记住的话

> **模型只会"提议",执行永远是 loop 的事。**

模型说"调用 read",不代表文件被读了——它只是吐出一个**意图**。真去读文件、把结果塞回对话、再叫模型继续的,是你写的 loop。这条对**任何** provider 都成立,所以它是整门课的地基。

## ① 先观察(别写代码)

跑这个,把一次完整运行"看见":

```bash
npm run demo:01
```

它会打印一条四步轨迹,并标出**每一行是谁产生的**。读懂它——尤其第②步(模型提议)和第③步(loop 执行)的区别。这就是你等下要亲手"跑出来"的东西。

## ② 认识零件(写预测前先读)

demo 给了你"画面",接下来去看这些画面在代码里叫什么——**打开 [`agent.ts`](./agent.ts),读最上面那几个类型定义**(到 `runAgent` 之前为止)。你 TS 底子好,直接读类型最快。重点认三个零件:

- **`history`(`HistoryEntry[]`)**:一个会越来越长的数组,记录至今发生的一切(= demo 打印的那几行)。
- **`role`**:每条 history 的"谁产生的"标记,共四种(`user` / `assistant-tools` / `tool-result` / `assistant-final`)。
- **`model.step(history)`**:你每问模型一次"下一步做什么"就调一次,调一次只走一步。

类型里都有注释。看完就有了预测所需的全部词汇。

## ③ 预测(写进 `LOG.md`,再往下)

认完零件,在 [`LOG.md`](./LOG.md) 写下预测(自己想,别问 tutor)。
这三题 demo 都**没直接给答案**,需要你自己推:

1. demo 只演了"调一次工具"的情况。**假如任务需要模型先后调用两次工具**(比如先 `read` A 文件、看完再 `read` B 文件),才能给出最终答复——
   那么这次 history 的 `role` 序列会变成什么样?`model.step()` 又会被调用**几次**?
   (这题逼你把 demo 那条轨迹"推广"——而这正是 loop 要能自动处理的。)
2. 回到 demo 那个"调一次工具"的场景:`model.step()` 被调用**几次**?为什么是这个数?
3. 那条 `tool-result`,是**模型**放进 history 的,还是**你的 loop** 放进去的?

先押注,才学得到。这一步不能跳——尤其第 1 题,它决定你的 loop 是"只会来回一次"还是"能一直转到结束"。
