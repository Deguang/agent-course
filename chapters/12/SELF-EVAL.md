# Capstone 自评框架

> 复制成 `SELF-EVAL.local.md` 再填。"程序跑完 ≠ 任务做对"——像 Day 10 讲的独立评测那样，拿证据说话，别只看"它没报错"。

## A. 功能:真的做成了吗(拿证据，别凭感觉)

- [ ] 用**设计文档第 2 节的可检验标准**逐条核对——每条贴出证据(实际输入 → 实际输出)。
- [ ] 至少准备 3 个 case:一个正常、一个边界、一个会失败的。分别记录 agent 的表现。
- [ ] 失败 case 里，agent 是**优雅处理**(工具异常当数据、报告清楚)，还是崩了/瞎编?

## B. 设计:判断力对不对

- [ ] 我选的那一格(raw/harness/loop/graph)真的合适吗?有没有**过度设计**(明明单 loop 够却上了 graph)?
- [ ] 如果重做，我会改哪个设计决定?为什么?

## C. 工程:可靠性

- [ ] 工具有没有安全边界(路径/命令)?知道边界是 guardrail 不是 sandbox 吗?
- [ ] 会不会跑飞(maxSteps)?会不会撑爆上下文(长任务)?
- [ ] 换一个 provider(Ollama ↔ 云端)，核心代码要改吗?(检验 provider 中立)

## C2. 生产健壮性(Day 11)
- [ ] agent 能作为**服务**被调用(SSE 流式)，不只是终端脚本?
- [ ] suspend→人工→resume 端到端跑通了?挂起态能序列化跨线、准确重入?
- [ ] 回归套件接成了 CI 门禁?故意改坏配置能被挡下?
- [ ] 高频场景考虑过语义缓存了吗(要/不要都要有理由)?

## D. 能不能讲清楚(终点检验)

用几句话回答(这是"专家 vs 会调 API"的分水岭):

- 我这个产品的核心是哪一格?为什么这一格够?
- 它的边界和风险在哪?
- 如果 AI 帮我生成了这套代码，我能看懂并指出它哪里会出问题吗?

> 三个都能答清楚 → 你已经是能独立设计开发 agent 产品的工程师了。答不清的地方，就是你下一步要补的。
